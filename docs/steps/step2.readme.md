# Step 2 – Building the Database with Flyway

> **In one line:** we wrote two SQL files. When the app starts, a tool called Flyway runs them and creates our 7 tables with sample data.

---

## Part 1 – The theory

### 1.1 The problem Flyway solves

You already know JPA. You may have used this setting:

```yaml
spring.jpa.hibernate.ddl-auto: update
```

With it, Hibernate looks at your `@Entity` classes and **creates or changes tables automatically**. That's easy, but it is risky in a real project:

- You can't see exactly what SQL ran.
- Hibernate never deletes or renames columns properly, so the database slowly drifts.
- Your laptop, your second computer and the AWS server can end up with **different** tables.
- There is no history of *when* and *why* the schema changed.

**Flyway fixes this.** Instead of Hibernate guessing, *we* write the SQL ourselves in numbered files. Flyway runs them in order, exactly once each.

> 💡 **Analogy:** Flyway is like **Git for your database**. Each SQL file is a commit. Flyway remembers which commits are already applied and only applies the new ones.

### 1.2 How Flyway works, step by step

1. You put SQL files in `src/main/resources/db/migration/`.
2. The file name must follow this pattern:

   ```
   V1__create_schema.sql
   │ │  └── description (anything, words separated by _ )
   │ └──── TWO underscores
   └────── V + version number
   ```

3. When Spring Boot starts, Flyway runs **before** Hibernate:

   ```
   App starts
     └─► Flyway looks at the table  flyway_schema_history
           ├─ V1 already there?  → skip
           ├─ V2 already there?  → skip
           └─ V3 is new?         → run it, then record it in history
     └─► Hibernate starts (only checks the tables, never changes them)
     └─► App is ready
   ```

4. `flyway_schema_history` is a table Flyway creates for itself. It is **not** one of our 7 tables, it's Flyway's notebook.

### 1.3 The one golden rule

> ⚠️ **Never edit a migration file after it has run.**

Flyway saves a *checksum* (a fingerprint) of every file it runs. If you change `V1` later, the fingerprint won't match and the app **refuses to start**.

**Need a change?** Create a new file, for example `V3__add_column_x.sql`.

### 1.4 Flyway and JPA together

In `application.yml` we set:

```yaml
spring.jpa.hibernate.ddl-auto: validate
```

That divides the jobs:

| Who | Job |
|---|---|
| **Flyway** | *Creates* and *changes* tables (the SQL files) |
| **Hibernate / JPA** | Only *checks* that your `@Entity` classes match the real tables. If they don't, the app stops with a clear error. |

That's why we build the database (Step 2) **before** the entities (Step 3).

### 1.5 Database concepts used in our SQL

| Concept | What it means | Example from our schema |
|---|---|---|
| **Primary Key (PK)** | Unique ID of each row | `customer_id` |
| **Foreign Key (FK)** | "This column must point to a real row in another table" | `customer_policy.customer_id` → `customer` |
| **Unique (UQ)** | No two rows can have the same value | Two customers can't share an `email` |
| **CHECK** | A rule each row must obey | `premium_amount > 0` |
| **Index** | Like a book's index; makes searching a column fast | Index on `full_name` for policy search |
| **Identity column** | The database generates the ID automatically (1, 2, 3, …) | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| **Trigger** | Code the database runs automatically on insert/update/delete | Blocks editing a payment |

**Why put rules in the database when Java will also check them?** It's a safety net. Even if a bug in our Java code slips through, the database refuses bad data.

### 1.6 Password hashing (BCrypt), in brief

We **never** store real passwords. We store a **hash**: a scrambled one-way version.

```
Password@123  ──BCrypt──►  $2a$10$yIAs3hkQS3urrRTDMP/DK.Lx...
```

- **One-way:** you can't turn the hash back into the password.
- **At login:** Spring Security (Step 4) hashes what the user typed and compares the two hashes.
- **The `{bcrypt}` prefix** in front of each hash tells Spring Security which algorithm was used. You'll see this in Step 4.

## Part 2 – What we built

Two files in `backend/src/main/resources/db/migration/`.

### `V1__create_schema.sql`: creates the 7 tables

```
customer ──────┬──< customer_policy >──── insurance_product
               │         │                      │
               │         └──< premium_installment
               │                   │            │
               │                   └──< premium_payment
               │                                │
               └──< ai_recommendation_request   │
                         │                      │
                         └──< ai_recommendation_item >──┘

  ──<  means "one-to-many"  (one customer has many policies)
```

| Table | Holds | Most important rule |
|---|---|---|
| `customer` | People who log in | Email is unique; birth date not in the future |
| `insurance_product` | The product catalog | Premium and sum insured > 0 |
| `customer_policy` | A product a customer bought | **One policy per customer per product** (duplicate rule) |
| `premium_installment` | Each scheduled payment of a policy | Paid amount ≤ scheduled amount + 10% penalty |
| `premium_payment` | Every actual payment made | **Can never be edited or deleted** (history) |
| `ai_recommendation_request` | Each time a customer asked the AI | Stores inputs, age, AI model name |
| `ai_recommendation_item` | Products the AI suggested | Same product can't appear twice in one request |

**Data types (required by the README):**
- Money → `NUMERIC(19,2)` (exact decimals, never `float`)
- Dates → `DATE`
- Created/updated time → `TIMESTAMPTZ` (time with time zone)

### `V2__seed_data.sql`: fills in sample data

This is the data from the README (section 5.5), so we have something to test with:
- **3 customers** (Aarav, Meera, Rohan). Password for all: **`Password@123`**.
- **3 products:** Term, Health, Savings.
- **2 policies**, their installments, 3 payments and 2 AI recommendations.

Two things we added:
- **The full payment schedule.** Aarav's policy is 20 years of monthly payments = **240 installments**, but the README only lists 3. We generate all 240, so the total matches ₹3,00,000.
- **ID counters moved forward.** We inserted rows with fixed IDs (1001, 1002…), so we tell PostgreSQL to continue numbering from there. Otherwise the next new customer would get ID 1 instead of 1004.

## Part 3 – Run and check

```powershell
cd backend
.\mvnw spring-boot:run
```

On the first run, Flyway applies V1 and V2. On later runs it skips them, because they're already in its history.

**Check in pgAdmin** (Query Tool on database `healthdekho`):

```sql
SELECT version, description, success FROM flyway_schema_history;
```
You should see V1 and V2, both `true`.

**Results verified on 2026-11-25:**

| Check | Result |
|---|---|
| Migrations applied | V1 ✅  V2 ✅ |
| Rows | 3 customers · 3 products · 2 policies · 241 installments · 3 payments · 2 AI requests · 3 AI items |
| Policy 3001 schedule total | 300000.00 ✅ |
| Try to edit a payment | Blocked: *"premium_payment rows are immutable"* ✅ |

### 🆘 Emergency reset (NOT a normal step)

You do **not** run this during setup. Use it only when something is broken during development, for example:
- you edited a migration that already ran, and the app now fails with *"Migration checksum mismatch"*;
- the sample data got messed up while testing and you want it fresh.

```sql
DROP SCHEMA public CASCADE; CREATE SCHEMA public;
```

This deletes all tables, including Flyway's history. On the next app start Flyway sees an empty database and runs V1 + V2 again, giving a clean copy.

⚠️ Only do this on your local dev database, never on a real one with real data.

-- DB-03: our constraints (hides Flyway's table and PostgreSQL 18's NOT NULL entries)
SELECT conrelid::regclass AS table_name,

## Quick recap

- **Flyway** = version control for the database. Numbered SQL files run once, in order.
- **Never edit** a file that already ran; add a new `V3__...` instead.
- **Flyway creates tables, Hibernate only validates them** (`ddl-auto: validate`).
- **The database itself enforces key rules** (unique, check, FK) as a safety net.
- **Passwords are stored as BCrypt hashes**, never as plain text.
